Hãy phân tích repository hiện tại và xây dựng bộ tài liệu context chuẩn dành cho AI coding.

CHẾ ĐỘ:
CONTEXT_BOOTSTRAP_ONLY

PHẠM VI:
- Chỉ phân tích repository và tạo/cập nhật tài liệu context.
- Không sửa source code, database, migration, cấu hình runtime hoặc business logic.
- Không chạy thao tác có thể làm mất dữ liệu.
- Không tự cài dependency hoặc thay đổi lockfile.

MỤC TIÊU:
Sau khi hoàn thành, một AI khác không có lịch sử chat hiện tại có thể đọc bộ tài liệu để:

- Hiểu project dùng để làm gì.
- Hiểu kiến trúc và module chính.
- Hiểu các business rule có bằng chứng.
- Biết các file, class, function, API và test quan trọng.
- Biết trạng thái hiện tại.
- Biết công việc đang làm, TODO, bug và rủi ro còn tồn tại.
- Tiếp tục công việc mà không cần đọc lại toàn bộ repository.

AI trong phiên sau vẫn phải kiểm tra source liên quan trực tiếp đến task.
Tài liệu context không thay thế việc xác minh source.

==================================================
1. KIỂM TRA TRƯỚC KHI PHÂN TÍCH
==================================================

Trước tiên:

1. Xác định repository root.
2. Kiểm tra `git status` bằng thao tác chỉ đọc.
3. Tìm tất cả `AGENTS.md` ở root, thư mục cha và các thư mục con liên quan.
4. Kiểm tra xem các file context sau đã tồn tại hay chưa:

- `AGENTS.md`
- `PROJECT_CONTEXT.md`
- `ARCHITECTURE.md`
- `BUSINESS_RULES.md`
- `CURRENT_STATE.md`
- `TODO.md`
- `BUGS.md`
- `README.md`

Nếu file đã tồn tại:

- Đọc đầy đủ trước khi cập nhật.
- Không ghi đè toàn bộ nếu có thể hợp nhất.
- Bảo toàn thông tin đúng và các thay đổi hiện có của người dùng.
- Xóa hoặc sửa nội dung lỗi thời chỉ khi có bằng chứng từ source/config/test.
- Nêu rõ mâu thuẫn giữa tài liệu và source.

Nếu file chưa tồn tại:

- Tạo file tại repository root.
- Không tạo bản trùng trong `docs/`.
- Bộ context tại root là nguồn canonical, trừ khi repository đã có quy ước khác.

Trước khi tạo file, báo cáo ngắn:

1. Project làm gì.
2. Stack được nhận diện.
3. Kiến trúc chính.
4. Module chính.
5. Tài liệu context đã có.
6. Tài liệu còn thiếu.
7. Nguồn bằng chứng sẽ sử dụng.
8. File dự kiến tạo hoặc cập nhật.

Sau báo cáo này, tiếp tục tạo tài liệu; không cần chờ xác nhận nếu chỉ tạo tài liệu và không có mâu thuẫn/rủi ro đáng kể.

==================================================
2. NGUỒN BẰNG CHỨNG
==================================================

Ưu tiên theo thứ tự:

1. Source, schema, migration, config và test đang được sử dụng.
2. Tài liệu chính thức hiện có.
3. Git history gần đây nếu có thể xác minh.
4. Comment, TODO, FIXME và placeholder trong source.
5. Suy luận của AI — chỉ được ghi dưới trạng thái `Chưa xác nhận`.

Quy tắc nguồn sự thật:

- Source hiện tại là nguồn xác minh trạng thái đã triển khai.
- Business rule được ghi là “đã xác nhận” chỉ khi có ít nhất một trong các bằng chứng:
  - Được tài liệu nghiệp vụ hiện có xác nhận.
  - Được người dùng xác nhận.
  - Được backend/database/workflow enforce rõ ràng.
  - Có test nghiệp vụ trực tiếp chứng minh.
- Source không được dùng để phủ nhận một business rule đã được tài liệu hoặc người dùng xác nhận.
- Nếu source và rule đã xác nhận mâu thuẫn, ghi rõ đây là sai lệch cần xử lý.
- Không tự sửa source trong task này.
- Nếu chưa chắc chắn, ghi `Status: Chưa xác nhận`.

Không suy diễn “ý định nghiệp vụ” chỉ từ tên field, giao diện hoặc comment đơn lẻ.

==================================================
3. PHẠM VI SOURCE CẦN ĐỌC
==================================================

Đọc có chọn lọc:

- Solution, workspace, project, package và config chính.
- Entry point và composition root.
- Cấu trúc thư mục/module.
- Domain entity/model quan trọng.
- Controller, endpoint, service, repository và data access chính.
- Database schema, migration, seed/bootstrap.
- Authentication, authorization, permission và data scope.
- Workflow, status transition, audit và snapshot.
- API/network/event/WebSocket nếu có.
- Worker, queue, scheduler hoặc background task nếu có.
- UI route, layout, form, state và luồng thao tác chính.
- Test quan trọng.
- README và tài liệu hiện có.
- Git diff hiện tại để tránh ghi đè thay đổi của người dùng.

Không cần đọc:

- `bin/`
- `obj/`
- `node_modules/`
- cache package
- build output
- coverage output
- generated source
- dependency source
- binary
- file log lớn
- secret hoặc giá trị credential

Có thể đọc tên biến cấu hình nhưng không đưa secret, token, password hoặc dữ liệu nhạy cảm vào tài liệu.

Nếu project lớn:

- Xác định kiến trúc và dependency flow trước.
- Đọc sâu module lõi và vùng đang hoạt động.
- Không đọc tuần tự từng file nếu không cần.

Phải bao gồm:

# Project
- Project là gì.
- Stack chính.

# Context bắt buộc
Mọi AI phải đọc trước khi sửa code:

1. `AGENTS.md`
2. `PROJECT_CONTEXT.md`
3. `ARCHITECTURE.md`
4. `BUSINESS_RULES.md`
5. `CURRENT_STATE.md`
6. `TODO.md`
7. `BUGS.md`
8. `README.md`
9. Tài liệu được các file trên tham chiếu.
10. Source và test liên quan đến yêu cầu hiện tại.

# Audit trước khi code
Trước khi sửa source, AI phải báo cáo ngắn:

1. Project làm gì.
2. Kiến trúc chính.
3. Công việc gần nhất.
4. Nội dung đã hoàn thành và bằng chứng.
5. Việc cần làm tiếp theo.
6. Bug/rủi ro còn lại.
7. File/module/API/test liên quan.
8. Patch tối thiểu dự kiến.

# Conflict gate
Nếu yêu cầu mới hoặc patch dự kiến vi phạm business rule/nguyên tắc đã xác nhận:

1. Dừng trước khi sửa code.
2. Chỉ rõ rule và file tài liệu liên quan.
3. Nêu tác động, rủi ro, trade-off và phương án thay thế.
4. Đề xuất nội dung tài liệu cần thay đổi.
5. Chờ người dùng xác nhận rõ việc sửa nguyên tắc.
6. Chỉ sau khi được xác nhận mới cập nhật tài liệu.
7. Sau đó mới được sửa code theo nguyên tắc mới.

Không tự ý vừa thay đổi rule vừa sửa code trong một quyết định ngầm.

Nếu source đang vi phạm rule đã xác nhận và task là đưa source về đúng rule:

- Không cần thay đổi rule.
- Nêu rõ sai lệch.
- Sửa source để tuân thủ rule khi task code được phép thực hiện.
- Cập nhật trạng thái và bằng chứng test.

# Quy tắc sửa code
- Patch nhỏ và đúng phạm vi.
- Không refactor ngoài task nếu không cần.
- Không sửa file không liên quan.
- Không thay đổi API, database, workflow, permission, ownership, pricing, snapshot hoặc kiến trúc nếu chưa có căn cứ.
- Frontend không được là nơi duy nhất enforce mutation nghiệp vụ quan trọng.
- Không ghi đè snapshot, lịch sử hoặc dữ liệu đã ký.
- Giữ UTF-8, BOM và line ending hiện tại.
- Bảo toàn thay đổi chưa commit của người dùng.
- Chạy kiểm tra phù hợp và báo rõ lệnh đã/không chạy.

# Cập nhật context
Sau thay đổi quan trọng:

- `CURRENT_STATE.md`: trạng thái đã triển khai.
- `TODO.md`: việc chưa làm/đang làm.
- `BUGS.md`: bug và rủi ro.
- `BUSINESS_RULES.md`: rule đã xác nhận.
- `ARCHITECTURE.md`: kiến trúc/API/data flow.
- `PROJECT_CONTEXT.md`: quyết định dài hạn.
- `AGENTS.md`: chỉ cập nhật khi quy trình bắt buộc thay đổi.

`AGENTS.md` không chứa:

- Lịch sử dài.
- TODO/bug chi tiết.
- Kiến trúc dài.
- Source code dài.

==================================================
11. BUGS.md
==================================================

Phân loại:

# Open Bugs

# Investigating

# Fixed Bugs

# Known Risks / Fragile Areas

Một vấn đề chỉ được ghi là bug xác nhận khi có một trong các bằng chứng:

- Có bước tái hiện.
- Có test fail trực tiếp.
- Có lỗi runtime/log.
- Có yêu cầu người dùng xác nhận triệu chứng.
- Có mâu thuẫn rõ giữa source và rule đã xác nhận.

Test fail do môi trường, dependency hoặc dữ liệu thiếu phải được phân loại đúng; không tự gọi là bug sản phẩm.

Mỗi mục nên có:

- Triệu chứng.
- Bằng chứng.
- Nguyên nhân nếu đã xác minh.
- Trạng thái.
- File/module.
- Workaround nếu có.
- Kiểm tra cần chạy lại.

Nếu chỉ nghi ngờ:

`Status: Suspected / Chưa xác nhận`

`Fixed Bugs` chỉ giữ bài học hoặc rủi ro hồi quy có giá trị lâu dài, không biến thành changelog vô hạn.
